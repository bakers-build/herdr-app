# Releases of the bakers mod: Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Version, tag and publish the bakers mod as GitHub releases (stable from `main`, `-next.N` pre-releases from `next`), with the version computed from Conventional Commits.

**Architecture:** Four small Bun scripts under `scripts/release/`:
- `conventional.ts`: pure parsing, bumping and notes.
- `version.ts`: reads git and implements the `release:version` CLI.
- `target.ts`: chooses the SHA to release on a branch push.
- `package.ts`: builds the ZIP and stamps the version.

`ci.yml` gets a `pr-title` job and a `release` job that call these scripts and `gh release create`. Docs and config switch the repo to `next` → `main`.

**Tech Stack:** Bun 1.4.4 (`bun test`, `Bun.spawnSync`), git, system `zip`/`unzip`, GitHub Actions, `gh` CLI on the runner.

**Spec:** `docs/superpowers/specs/2026-11-17-release-design.md` (approved 2026-11-17). Read it before any task.

## Global Constraints

- Bun `1.4.4`. No new dependencies; only `node:` modules, `Bun` APIs, git, `zip`/`unzip`.
- **Stable tag:** `v<MAJOR>.<MINOR>.<PATCH>`. **Pre-release tag:** `v<X.Y.Z>-next.<N>`. The CLI prints versions without the `v`.
- **Releasable types:** `feat` (minor), `fix`/`perf` (patch), breaking (`!` or a `BREAKING CHANGE:`/`BREAKING-CHANGE:` footer). Breaking bumps minor while major is 0, else major. All other types release nothing.
- **Known types for PR titles:** `feat fix perf chore docs ci test refactor style build revert`.
- Only a commit's first line is a header. A body counts only for breaking footers. Merge commits are skipped.
- **Notes sections, in order:** `### Breaking changes`, `### Features`, `### Fixes`. **Bullet:** `- **scope:** subject (abc1234)`, or `- subject (abc1234)`. Newest first.
- **Repo `mods/bakers/mod.json`:** `{ "place": "none", "version": "0.0.0-dev" }`. `package.json` gets no `version`.
- **ZIP:** `dist/herdr-bakers-<version>.zip`, top folder `herdr-bakers-<version>/` containing `mods/bakers/**`, `scripts/install.ts`, `scripts/layout.js`, `README.md`.
- **Non-merge push to `main` after a stable tag:** the error text is `main takes merge commits from release branches only`.
- CI: keep the existing commit pins. PR titles reach scripts only through `env:`.
- `.bakers/project.config.js` is edited only in the `working` state (it is read-only during plan).

## Review Focus

1. **A repo with no tags at all** (the bootstrap). `release:version` must use base `0.0.0` and give `0.1.0` when a `feat` exists. Test in Task 2: `bootstraps from 0.0.0 without tags`.
2. **A pre-release tag reachable from the SHA.** It must not count as the stable base: with `v0.1.0` and `v0.2.0-next.1`, a stable run still bumps from `0.1.0`. Test in Task 2: `ignores pre-release tags for the stable base`.
3. **A rerun after the tag exists.** The output is empty and the exit code 0. Test in Task 2: `prints nothing once the SHA is tagged`.
4. **Commit subjects with Markdown or odd characters** (backticks, `#123`, a colon in the subject). They pass through verbatim, and only the first `: ` splits. Test in Task 1: `keeps the subject after the first colon verbatim`.
5. **An installer run from an unpacked ZIP in a path with spaces.** It must find its `mods/` folder. Test in Task 3: `installs from an unpacked package in a path with spaces`.

### Task 1: Conventional Commits parsing, bump and notes

**Files:**
- Create: `scripts/release/conventional.ts`
- Test: `tests/release-conventional.test.ts`

**Interfaces:**
- Produces:
  - `type Commit = { sha: string; subject: string; body: string }`
  - `type Change = { sha: string; type: string; scope: string | null; breaking: boolean; subject: string }`
  - `KNOWN_TYPES: readonly string[]`
  - `parseHeader(line: string): { type: string; scope: string | null; bang: boolean; subject: string } | null`. Regex `^(\w+)(?:\(([^)]+)\))?(!)?: (.+)$`. Returns `null` when the type is not in `KNOWN_TYPES`.
  - `toChange(c: Commit): Change | null`
  - `bump(version: string, changes: Change[]): string | null`. `null` when nothing releasable.
  - `renderNotes(changes: Change[]): string`

- [ ] **Step 1: Write failing tests.** Cover:
  - `parseHeader("feat(ticket)!: add x")` → `{type:"feat", scope:"ticket", bang:true, subject:"add x"}`.
  - `parseHeader("Merge branch x")` → `null`.
  - `parseHeader("feature: x")` → `null`.
  - `keeps the subject after the first colon verbatim`: `parseHeader("fix: a: b \`c\` #12").subject === "a: b \`c\` #12"`.
  - `toChange` with body `"BREAKING CHANGE: y"` → `breaking: true`.
  - A body line `* feat: z` alone gives no breaking and does not change the type.
  - `bump`:
    - `("0.0.0",[feat])` → `"0.1.0"`
    - `("0.1.0",[fix])` → `"0.1.1"`
    - `("0.1.3",[breaking fix])` → `"0.2.0"`
    - `("1.2.3",[breaking])` → `"2.0.0"`
    - `("1.2.3",[feat, fix])` → `"1.3.0"`
    - `("1.2.3",[chore])` → `null`
  - `renderNotes`: sections appear in the fixed order, an empty section is omitted, and a bullet is `- **ticket:** add x (abc1234)` with the 7-character SHA.

- [ ] **Step 3:** Implement the interfaces above in `scripts/release/conventional.ts`. `renderNotes` filters to releasable changes. A breaking change appears only under *Breaking changes*.

### Task 2: `release:version` against git

**Files:**
- Create: `scripts/release/version.ts`, `tests/git-fixture.ts` (helper: temp repo with `git init -b main`, local `user.name`/`user.email`, `commit(msg)`, `tag(name, sha?)`, `merge(branch)`)
- Modify: `package.json` (script `"release:version": "bun scripts/release/version.ts"`)
- Test: `tests/release-version.test.ts`

**Interfaces:**
- Consumes: Task 1.
- Produces:
  - `nextRelease(opts: { cwd: string; sha: string; pre?: "next" }): { version: string; notes: string } | null`
  - CLI `bun scripts/release/version.ts <SHA> [--pre next] [--notes <file>|-]`. Line 1 is the version; with `-`, a blank line and the notes follow. Empty output and exit 0 when `null`. A bad SHA exits 1 with a message on stderr.

Algorithm (not fixed by the tests alone):

```
stableBase = git describe --tags --abbrev=0 --match 'v[0-9]*' --exclude '*-*' <sha>   (none → root, "0.0.0")
commits    = git log --no-merges --format=%H%x1f%s%x1f%b%x1e <stableBase>..<sha>   (or <sha> when none)
version    = bump(base, changes(commits)); null → null
pre:       notesFrom = git describe --tags --abbrev=0 --match 'v[0-9]*' <sha>  (any tag kind)
           changes since notesFrom; none releasable → null
           N = 1 + max n over `git tag -l "v<version>-next.*"`; version += "-next.N"
```

- [ ] **Step 1: Write failing tests** with the fixture:
  - `bootstraps from 0.0.0 without tags`: commits `chore: init`, `feat: a`, `fix: b` → `0.1.0`. The notes contain `### Features` and `### Fixes`.
  - `bumps from the last stable tag`: after `v0.1.0`, `fix: c` → `0.1.1`, and the notes list only `c`.
  - `prints nothing once the SHA is tagged`: tag HEAD `v0.1.1` → `null`. The CLI's stdout is `""` and its exit code 0.
  - `prints nothing for chores only`.
  - `ignores pre-release tags for the stable base`: `v0.1.0`, `feat: d`, tag `v0.2.0-next.1`, `fix: e` → stable `0.2.0`.
  - `numbers pre-releases`: same repo, `pre: "next"` → `0.2.0-next.2`, and the notes list only `e`.
  - `sees the tag on the frozen SHA from next`: branch `next` with `feat: f`. Merge it into `main` with `--no-ff`, tag `HEAD^2` as `v0.3.0`. Then `feat: g` on `next` → `0.4.0`.
  - CLI `--notes -` prints `0.1.0\n\n### Features…`. `--notes <file>` writes the file and prints only the version.
- [ ] **Step 2:** Run `bun test tests/release-version.test.ts`. Expected: FAIL.
- [ ] **Step 3:** Implement `nextRelease` and the CLI. Run git with `Bun.spawnSync(["git", ...], { cwd })`, and throw with git's stderr on failure.
- [ ] **Step 4:** Run `bun test tests/release-version.test.ts`. Expected: PASS.
- [ ] **Step 5:** Commit `feat(release): add release:version computing the next version from git`.

The CLI `bun scripts/release/target.ts <branch>` prints `sha=<sha>` and, on `next`, `pre=next`, as `$GITHUB_OUTPUT` lines.
